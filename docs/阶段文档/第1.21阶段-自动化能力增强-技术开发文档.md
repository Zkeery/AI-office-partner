## 一、背景
- 1.19 之后，自动化列表只能看见「最近一次」跑次：时间、成败摘要、点进对应任务。
- 产品侧常见下一问：「上次之前呢？」「失败了有没有提醒？」「能不能任务完成后自动再跑？」——分别对应跑次历史、结果通知、事件触发。
- 当前数据模型（`Schedule`）仅有 `last_run_at` / `last_task_id` / `last_error` 三个「最近一次」字段；本刀新增 `schedule_runs` 流水表。

## 二、阶段目标（候选，均标注可选）
本阶段是「能力增强候选池」，**不默认一次全做**。候选如下：

1. **跑次历史**（已实现）  
   - 每个自动化保留最近 N 次成功/失败记录；列表可展开；单条可点进对应任务。
2. **结果通知**（本刀已实现）  
   - **站内提示优先**（toast + 自动化页未读横幅 + 侧栏角标）；明确**不做**邮件推送、**不做** crontab 外发。
3. **事件触发**（可选 / 未做，风险高）  
   - 如「某任务完成 → 触发另一自动化 / 下游动作」；需单独设计触发图、循环防护与权限边界。

## 三、非目标
- 不引入复杂 crontab 表达式或外部 cron 守护。
- 不做邮件 / 短信 / 飞书机器人等外发通知（除非产品书面另定并另开阶段）。
- 不在本阶段实现通用事件总线或「任务完成 → 任意下游」编排。
- 不改坏 1.18/1.19 已有列表字段与「最近一次」点进行为。
- 本刀不做事件触发；不做邮件/短信/飞书机器人等外发。

## 六、数据 / API（本刀落地）

### 6.1 跑次历史
- **表** `schedule_runs`  
  - `id`、`schedule_id`、`task_id`（可空）、`started_at` / `finished_at`、`status`（success|failed）、`error`（可空）、`trigger`（manual|interval）
- **写入**：`trigger_schedule` 在 stamp `last_*` 的同时 append 一条 run；失败路径同样写；按 `SCHEDULE_RUN_KEEP`（默认 20）裁旧。
- **读取**：`GET /api/schedules/{id}/runs?limit=N`；列表页默认仍只露 `last_*`，点「跑次历史」再拉。
- **淘汰**：按 schedule 保留最近 N 条（写时裁）。

### 6.2 结果通知（本刀落地）
- **读取**：`GET /api/schedules/notices?limit=N&status=success|failed`（可选 status）；跨自动化汇总最近跑次，含 `run_id` / `schedule_id` / `schedule_name` / `task_id` / `status` / `error` / `finished_at`。
- **已读水位**：前端 `localStorage`（`ai_office_sched_acked_runs`）记录已读 `run_id`；刷新后未读失败仍可见。
- **UI**：右下角 toast（立即跑 / 打开时最新未读失败）；自动化页失败未读横幅；侧栏「自动化」角标。
- **不做**邮件队列、外部 webhook、crontab 外发。

### 6.3 事件触发（可选，仅占位）
- 需另文：触发源、过滤器、动作、防环、权限。
- **本阶段不做。**

## 七、风险
| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 范围膨胀 | 历史 + 通知 + 事件一次做，易拖成大刀 | 本刀只做历史 |
| 存储膨胀 | 每次跑都写流水，长期涨库 | 强制最近 N；索引 `schedule_id` |
| 与 last_* 双写不一致 | 流水有、last_* 无（或相反） | 同一服务函数内双写；测失败路径 |
| 通知骚扰 | 站内提示过频 | 失败未读为主；可一键全部已读；toast 约 8s 自动收 |
| 事件触发环 | A 完成触发 B，B 再触发 A | 本阶段不做 |
