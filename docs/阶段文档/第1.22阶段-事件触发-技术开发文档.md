## 一、背景与现状

### 1.1 已有自动化能力
| 能力 | 现状 |
| --- | --- |
| 数据模型 `schedules` | `interval_minutes` / `enabled` / `next_run_at` / `last_*`；无触发方式字段 |
| 触发入口 | 仅两种：`manual`（`POST .../run-now`）与 `interval`（`scheduler_loop` 每 30s 扫到期项） |
| 跑次流水 `schedule_runs` | 已有 `trigger` 字段（`manual` \| `interval`），可扩展新取值 |
| 站内通知 | `GET /api/schedules/notices` + 前端 toast/横幅/角标（1.21） |
| 任务终态钩子 | `run_agent_job` 成功时写 `status=succeeded` 并 `append_event(..., "done")`；**尚无**调度侧监听 |
| 资料库 | 授权文件夹按需读；**无**文件变更监听 |

### 1.2 产品语境（摘自 1.21）
常见下一问含：「能不能任务完成后自动再跑？」——即应用内事件触发。  
此前明确后置原因：需触发条件、防环、权限与失败语义，不宜与跑次/通知同刀。现产品决定两刀都纳入 1.22，先排期再实现。

## 二、阶段目标
让自动化除「到点 / 立即跑」外，支持两种事件触发切片：**刀 1：应用内自动化 A 成功后触发 B**；**刀 2：带密钥的入站 Webhook 触发指定自动化**。两刀均需在跑次历史里区分触发来源；范围可控、可验收，不引入系统级 cron 与邮件外发。

## 三、非目标
- **不做**系统级 crontab / 复杂 cron 表达式编辑器 / 外部 cron 守护。
- **不做**邮件 / 短信 / 飞书机器人等外发通知（除非产品书面另定并另开阶段）。
- **不做**资料库文件变更监听。
- **不做**多级链式编排（A→B→C…）；本阶段刀 1 只允许 A→B。
- **不做**通用事件总线、可视化编排图、「任意事件 → 任意下游」工作流引擎。
- **不做**出站 Webhook（把结果推到外部 URL）；刀 2 仅做入站 Webhook。
- 不改坏 1.18–1.21 的间隔调度、立即跑、`last_*`、跑次历史、站内通知行为。

## 四、双切片与推荐实现顺序

产品决定 1.22 两刀都做，先排期再实现：

### 4.1 刀 1：应用内「任务成功完成 → 触发指定自动化」


**切片定义**  
- 创建/编辑自动化时可选触发方式：`interval`（现有）或 `on_task_succeeded`。  
- 选后者时绑定「监听范围」之一（建议第一刀只做最简）：  
  - **A（更简）**：任意手动任务成功完成即触发该自动化（可附可选 `skill_id`/`expert_id` 过滤，可选）；或  
  - **B（更准）**：绑定某一个源 `task_id` / 或「与本自动化同 prompt 族」——**推荐默认 B 的弱化版：绑定「指定任务 ID」或「指定自动化跑出的任务成功后再跑本条」**。  
- **第一刀落地建议（可交付）**：  
  1. `Schedule` 增加 `trigger_mode`：`interval` \| `on_task_succeeded`（默认 `interval`）。  
  2. 增加可选 `listen_schedule_id`：当「另一条自动化」产生的任务成功完成时，触发本条（链式「A 跑完再跑 B」）。  
  3. 任务成功落库后调用轻量分发：查找 `enabled && trigger_mode=on_task_succeeded && listen_schedule_id==源 schedule`（源任务由自动化创建时需在 task meta 记 `schedule_id`；手动任务若无 schedule 则不触发链式）。  
  4. 调用现有 `trigger_schedule(..., trigger="task_done")`；跑次历史可见 `trigger=task_done`。  
  5. **防环**：同一调用链 `depth ≤ 1`（第一刀只允许 A→B，禁止 B 再触发他人）或 `visited_schedule_ids` 集合；禁止自触发（`listen_schedule_id != self`）。

**为何推荐**  
- 与 1.21 产品原话对齐，验收场景清晰：「自动化 A 成功 → 自动跑 B」。  
- 复用 `trigger_schedule` / `schedule_runs.trigger` / 站内通知，增量小。  
- 钩子点明确（任务 `succeeded` 之后），无需新守护进程。  
- 本地自用产品无公网暴露需求，比 Webhook 更贴现架构。

### 4.2 刀 2：入站 Webhook（带密钥）

**切片定义**  
- `POST /api/hooks/schedules/{schedule_id}`（或 `/api/schedules/{id}/trigger`），Header/`?token=` 校验。  
- 每条自动化可生成/轮换 `hook_token`（存库，列表可「复制触发 URL」）。  
- 校验通过后 `trigger_schedule(..., trigger="webhook")`。  
- UI：自动化详情展示「Webhook URL + 重置密钥」；仍保留间隔与立即跑。

**何时选备选**  
- 产品明确要接 Shortcuts / 外部脚本 / 其他本机工具「推一把」。  
- 可接受本机 token 泄露风险与「仅本机/局域网」说明。

**相对推荐刀的代价**  
- 鉴权、token 轮换、误触发面；本地默认只绑 127.0.0.1 时外部工具还要额外隧道——与「个人本地」定位略冲。

### 4.3 推荐实现顺序
**先刀 1，后刀 2。**

- **先做刀 1 的理由**：应用内可在本地直接验收，且复用现有 `trigger_schedule`、跑次记录与站内通知，增量和验证面更小。
- **后做刀 2 的理由**：需要单独处理密钥生成/存储/轮换、鉴权失败语义与本机接口暴露边界；放在刀 1 之后可复用触发、跑次与通知基础设施。

### 4.4 明确后置（本阶段不切）
| 方向 | 原因 |
| --- | --- |
| 资料库文件变更触发 | 无 watcher；抖动/防抖/权限与跨平台成本高 |
| 任务失败也触发 / 条件表达式 | 语义与费用面扩大，留续刀 |
| 多级链式（A→B→C…） | 防环与费用叠加；刀 1 只允许 A→B |
| 出站通知到邮件/飞书 | 与既有非目标冲突 |

## 五、数据模型 / API / UI 草案（按双刀与推荐顺序）

### 5.1 数据模型
`schedules` 增列（草案名可微调）：
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `trigger_mode` | str | `interval`（默认）\| `on_task_succeeded` |
| `listen_schedule_id` | str? | 仅 `on_task_succeeded`：监听哪条自动化产出的任务成功；FK 逻辑删除时置空或禁用 |
| `hook_token` | str? | 刀2：入站 Webhook 密钥（轮换后旧值失效；列表不回说明文） |

可选（若实现时发现源任务难关联）：在由自动化创建的 task `plan_json` / meta 中写入 `source_schedule_id`（创建任务时已有 schedule 上下文，改动面小）。

`schedule_runs.trigger` 新增取值：`task_done`、`webhook`。

**不做**：独立 `events` 总线表（第一刀不需要）。

### 5.2 API 草案
| 方法 | 路径 | 说明 |
| --- | --- | --- |
| 现有 | `POST /api/schedules` / `PATCH ...` | body 增 `trigger_mode`、`listen_schedule_id`；`on_task_succeeded` 时可允许 `interval_minutes` 仅作占位/忽略到期扫 |
| 现有 | `POST .../run-now` | 不变；仍为 `manual` |
| 内部 | 任务成功后的分发函数 | 无独立公开 API；测测服务层即可 |

刀 2：`POST /api/schedules/{id}/hook`（Header `X-Hook-Token` 或 `?token=` / Bearer）；`POST /api/schedules/{id}/rotate-hook-token`（明文密钥仅本次返回）。

### 5.3 调度行为
- `tick_due_schedules`：**只扫** `trigger_mode=interval`（或 `enabled` 且非纯事件模式），避免事件型自动化被 interval 误跑。  
- `on_task_succeeded`：不依赖 `next_run_at`；成功分发时仍更新 `last_*` 与 `schedule_runs`。  
- 事件触发失败：写 `last_error` + run 失败行；**不**自动重试风暴（第一刀失败即停，靠站内通知）。

### 5.4 UI 草案（自动化页）
- 创建/编辑表单增加「触发方式」：到点重复 / 某自动化成功后。  
- 选后者：下拉选择「监听哪条自动化」（排除自己）。  
- 列表行展示触发方式文案（如「A 成功后」）；跑次历史显示 `task_done`。  
- 站内通知文案可带触发来源（可选，非验收硬项）。

## 七、风险与依赖

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 触发环 / 费用叠加 | A↔B 或长链狂跑 | 第一刀 depth≤1 + 禁自指；续刀再谈多级 |
| 与 interval 双模式混淆 | 事件型仍被 tick 扫到 | tick 过滤 `trigger_mode` |
| 源任务关联丢失 | 手动任务无 schedule_id | 第一刀只监听「自动化产出的任务」；文档写清 |
| 成功定义歧义 | 计划失败 / 执行失败 | 仅 `succeeded` 触发；failed 不触发 |
| 异步时序 | 成功 commit 前后分发 | 在 status 已成功并 commit 后分发；分发失败记 B 的 last_error |
| 范围膨胀 | 顺手做文件监听/邮件 | 非目标写死；本轮只文档 |

**依赖**：1.21 已通过（跑次 + 通知）；任务成功路径稳定（`run_agent_job`）。
